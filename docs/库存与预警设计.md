# 货架库存与库存预警设计

> 目标：把「入库」和「上架」两个概念拆开，让收银台有真实可售库存，并对低库存做分级预警。

## 1. 三层库存模型

```
在途 (pending_in)     已下采购订单、尚未收货
   │ 收货入库（采购订单收货 → 采购入库单）
   ▼
仓库 (warehouse)      收货后进入仓库
   │ 上架（上架单）
   ▼
货架 (shelf)          可售库存 —— POS 销售扣减的就是这一层
```

`wms_stock` 一行 = 一个「门店 × 商品」的库存，同时持有 `warehouse_quantity` 和 `shelf_quantity`。
在途数量不落库，由「采购订单明细的 ordered_qty − received_qty」实时汇总得出（`pendingInQuantity`）。

**收银台可售量 = shelf_quantity**，这是整个设计的关键点。

## 2. 单据职责矩阵

| 动作 | 在途 | 仓库 | 货架 | 单据 | 是否需要审核 |
|---|---|---|---|---|---|
| 采购收货 | − | **+** | — | 采购入库单（收货入库，来源采购订单） | 入库即审核 |
| **上架/补货** | — | **−** | **+** | **上架单** | **否** |
| 调拨 | — | 源 **−** / 目标 **+** | — | 调拨单（出库单 outType=2） | 是 |
| 报损 | — | **−** | — | 出库单 outType=3 | 是 |
| 其他出库 | — | **−** | — | 出库单 outType=4 | 是 |
| POS 销售 | — | — | **−** | 销售订单 | 否 |
| 采购退货 | — | **−** | — | 采购退货单 | 是 |
| 盘点 | — | 调整 | 调整 | 盘点单 | 是 |

**为什么上架不设审核**：上架是同一门店内「仓库 → 货架」的物理移动，不涉及金额、不涉及外部方、不影响对账。超市一天补货多次，加审核只会拖慢收银。

**为什么上架不塞进「出库单」**：出库单 = 货物离开门店（调拨/报损/其他）。上架货物没离开，用「出库」表达会误导操作者。

> 兼容说明：`wms_stock_out.out_type = 1` 在旧实现里被注释为「销售出库」，实际效果是「仓库 → 货架」，即上架。
> 前端从未产生该类型（出库固定 4、调拨 2）。引入上架单后，`out_type=1` 视为历史遗留，新业务不再使用。

## 3. 库存预警

### 3.1 阈值来源（商品级默认 + 门店级覆盖）

| 表 | 字段 | 说明 |
|---|---|---|
| `pms_product` | `stock_warn_threshold` | 商品默认预警线，默认 10 |
| `pms_product` | `stock_urgent_threshold` | 商品默认紧急线，默认 3 |
| `wms_stock` | `warn_threshold` | 门店级覆盖，`NULL` 表示沿用商品默认 |
| `wms_stock` | `urgent_threshold` | 门店级覆盖，`NULL` 表示沿用商品默认 |

生效值 = `COALESCE(stock.warn_threshold, product.stock_warn_threshold)`

按「门店 × 商品」覆盖的必要性：同一商品在旗舰店和社区店销量差几倍，统一阈值必然一边误报一边漏报。

### 3.2 四档状态（按货架库存判定）

| 条件 | `stockStatus` | 含义 |
|---|---|---|
| `shelf = 0` | `out_of_stock` | 缺货，无法销售 |
| `0 < shelf ≤ urgent` | `urgent` | 紧急 |
| `urgent < shelf ≤ warn` | `warning` | 预警 |
| `shelf > warn` | `normal` | 正常 |

### 3.3 补货方式（区分「找谁」）

预警时进一步判断货源，给出可执行的动作：

| 条件 | `replenishType` | 提示 | 动作 |
|---|---|---|---|
| `warehouse > 0` | `shelf_up` | 仓库可补货 | 生成上架单 |
| `warehouse = 0` 且 `pending_in > 0` | `in_transit` | 在途补货中 | 等待收货，无需处理 |
| 都为 0 | `purchase` | 需采购 | 去采购下单 |

这一层把「一个红色数字」变成「该催仓库还是该催采购」，是预警真正有用的前提。

## 4. API

### 4.1 上架单 `/api/v1/stock/shelf-ups`

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/stock/shelf-ups` | 分页（shelfUpNo/storeId/status/时间范围） |
| GET | `/api/v1/stock/shelf-ups/{id}` | 详情（明细含当前仓库/货架库存） |
| POST | `/api/v1/stock/shelf-ups` | 新建（草稿） |
| PUT | `/api/v1/stock/shelf-ups/{id}` | 编辑（仅草稿） |
| DELETE | `/api/v1/stock/shelf-ups/{id}` | 删除（仅草稿） |
| PUT | `/api/v1/stock/shelf-ups/{id}/confirm` | 确认上架：仓库 −、货架 + |
| PUT | `/api/v1/stock/shelf-ups/{id}/rollback` | 撤销上架：货架 −、仓库 + |

**状态**：`0 草稿 / 1 已上架 / 2 已撤销`

**校验**：
- 确认上架：`warehouse_quantity ≥ 本次上架量`，否则整单拒绝（先整体校验，避免部分成功）
- 撤销上架：`shelf_quantity ≥ 本次上架量`，否则拒绝（可能已部分售出）

### 4.2 库存查询 `GET /api/v1/stock`

在原参数基础上新增 `warnLevel`：

| 值 | 含义 |
|---|---|
| 空 | 全部 |
| `warning` | 所有非正常（含紧急、缺货） |
| `urgent` | 仅紧急 |
| `out_of_stock` | 仅缺货 |

**返回新增字段**：`warehouseQuantity`、`shelfQuantity`、`pendingInQuantity`、`totalQuantity`、`warnThreshold`、`urgentThreshold`、`thresholdOverridden`、`stockStatus`、`replenishType`

## 5. 库存日志类型

| `log_type` | 含义 |
|---|---|
| 1 | 采购入库 |
| 2 | 手动入库 |
| 3 | 手动出库 |
| 4 | 销售出库（历史） |
| 5 | 盘点调整 |
| 6 | 入库回退 |
| **7** | **上架（仓库 → 货架）** |
| **8** | **上架撤销（货架 → 仓库）** |
| **9** | **调拨入库（目标门店仓库 +）** |

> 上架/撤销的日志 `before_stock` / `after_stock` 记录的是**仓库库存**，货架变化写在 `remark` 里。

## 6. 页面

| 路由 | 页面 | 说明 |
|---|---|---|
| `/warehouse/stock` | 库存查询 | 展示在途/仓库/货架/合计/阈值/状态，支持预警筛选 |
| `/warehouse/shelf-up` | 上架单 | 上架单列表与办理 |
| `/warehouse/stock-warning` | 库存预警 | 只看预警商品，按补货方式给出动作 |
| `/pos/checkout` | 收银台 | 低库存角标与加购提示 |

侧边栏顺序：库存查询 → 上架单 → 库存预警 → 收货入库 → 出库单 → 调拨 → 盘点

## 7. 数据迁移

| 脚本 | 作用 |
|---|---|
| `upgrade-shelf-inventory.sql` | 建 `wms_shelf_up` / `wms_shelf_up_item`，加四个阈值字段 |
| `init-shelf-stock.sql` | 把现有仓库库存的 50% 搬到货架（一次性，可重复执行） |
| `seed-shelf-inventory-menu.sql` | 新增菜单与权限 |

`init-shelf-stock.sql` 是必要的：上架功能此前不存在，`shelf_quantity` 全为 0，而 POS 扣的正是这一层，不搬货则收银台无法销售。如不希望自动搬货，跳过该脚本、改成在界面手工做上架单即可。
